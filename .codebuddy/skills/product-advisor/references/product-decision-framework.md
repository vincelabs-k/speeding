# 产品决策框架

讨论需求优先级、竞品定位、版本规划与指标时使用的通用框架。只产出讨论内容，
不落盘任何决策文档。

## 1. 需求优先级评估（价值 / 成本 / 风险）

对每个需求给出三要素评分（1–5），再合成结论：

| 要素 | 问题 | 低分(1) | 高分(5) |
|---|---|---|---|
| 价值 | 解决多少人、多频繁、多大痛点 | 小众低频 | 目标用户高频核心痛点 |
| 成本 | 实现 + 维护 + 认知成本 | 高 | 低 |
| 风险 | 破坏现有体验/主张的概率 | 低 | 高 |

- 推荐取舍：价值高且成本低 → 做；价值高成本高 → 拆小步；价值低成本高 → 不做；
  风险高 → 先论证「存在理由四问」再谈。
- 输出形态：每个需求给「做 / 不做 / 后置」+ 一句理由，用户拍板。

## 2. 竞品对照维度

- **功能边界**：双方都有什么、单方有什么（对照表）。
- **目标用户**：各自服务谁——Speeding 服务「想一次设好就忘」的人，VSC 服务
  「想完全掌控」的人；不完全重叠，不要盲目对齐功能表。
- **差异化**：我们独有的（站点记忆、零追踪、保持音调）如何叙事、如何被感知。
- 判断法：对照结论分三类——差异（保持）、补全（有真实痛点缺口才补）、跟风
  （VSC 有而我们的用户不需要，跳过）。

## 3. 版本规划

- 目标：每次发布一个清晰主题，认知增量可控。
- 规划步骤：
  1. 列出候选功能池（含未做/待做/待砍）。
  2. 按「存在理由四问」过滤出候选集。
  3. 按依赖关系与价值/成本排序为里程碑。
  4. 每个里程碑命名一个用户可感知的主题（例：「站点记忆增强」而非「内部重构」）。
- 反模式：把所有积压需求一次排入下个版本；把技术重构伪装成用户价值。

## 4. 成功指标定义

- 每个功能上线前定义可观测指标（不依赖埋点也能收集的优先）：
  - 激活：安装后多久首次使用倍速、首次设置站点记忆。
  - 使用：倍速切换次数、站点记忆命中率（记忆设置后被重复访问站点的命中）。
  - 留存：安装后第 7 天 / 30 天仍在使用。
  - 口碑：商店评分、评价中「简单/好用/安静」类词频。
- 指标要与价值主张挂钩：对 Speeding，「用户少操作」优于「功能被多用」——
  倍速被高频切换可能意味着记忆失败而非成功。
- 每个指标说明「为什么这个数字变好 = 产品变好」，防止指标与用户价值脱钩。
