# 功能取舍「恰当性」框架（Fitness-First）

产品功能取舍的核心不是「极简」也不是「最少」，而是「**最恰当**」——功能在多与少
之间取平衡点。判断标准不是「能不能砍」，而是「**这个功能是否有不可替代的存在理由**」。

## 行业共识依据（对齐专业人士看法）

| 来源 | 主张 | 拆解 |
|---|---|---|
| 张小龙 | 「克制是产品经理的本能」 | 反对的是**打扰用户的功能**，不是功能数量；微信功能不少——「该有的要有，不该有的坚决不要」 |
| 乔布斯 | "Simplicity is the ultimate sophistication" | iPhone 不是功能最少，而是每个功能被精心设计到可发现、可理解、恰到好处 |
| 37signals | 砍功能的判断标准 | 看「解决多少人的多少频率问题」，不为极简而极简；砍是为了护住核心，不是表演克制 |
| 行业共识 | featuritis（功能膨胀）是病 | 但空壳产品（功能不足、核心任务完不成）同样是失败——恰当是中间平衡点 |

关键区分：**极简（minimal）≠ 最少（minimal-feature）**。专业共识是「本质极简」：
去掉不必要，保留必要，判断标准是每个功能是否有不可替代的存在理由。

## 存在理由四问

评估任何功能（新增 / 改造 / 砍除）时逐问：

1. **解决谁的什么问题？**
   - 要能说出具体用户 + 真实场景（例：课程学习者连续看 40 分钟 Bilibili 讲座）。
   - 拒绝「可能有人需要」这类无主语陈述。
2. **不做会怎样？**
   - 损失能否具体描述（时间、操作步骤、放弃使用）？
   - 还是只是「感觉少点什么」？
3. **服务核心价值主张吗？**
   - 对 Speeding：是强化 *set it once and forget it*，还是偏离它？
   - 判断法：见下「破坏 vs 强化核心主张」。
4. **复杂度与收益匹配吗？**
   - 实现成本、UI/交互占用、用户认知成本、长期维护成本 vs 收益。

四问全过 → 恰当；任一不过 → 不恰当或可后置。

## 双极端警示（判断当前提案偏向哪端）

- **功能膨胀（featuritis）**：为覆盖所有用户而堆功能 → 核心被淹没、设置项膨胀、
  选择过载、每次更新都增加学习成本。症状：功能清单越来越长而「默认路径」越来越短。
- **空壳产品（过度削减）**：砍过头导致核心任务完不成、价值主张落空。症状：删掉后
  用户必须用多个工具拼凑才能完成原本一键完成的事。

讨论时必须显式指出：当前提案靠近哪个极端、风险在哪，再谈取舍。

## 核心主张判断法：破坏 vs 强化

对 Speeding 的任何功能提案，用核心主张 *set it once and forget it* 做二分：

- **强化主张**（合理加分项，评估后纳入）：
  - 减少操作次数（如站点级记忆让重复访问零操作）。
  - 减少打扰（如不打扰式反馈、默认即正确）。
- **破坏主张**（默认拒绝，除非有强理由）：
  - 增加每次使用的认知负担（复杂设置面板、多级菜单）。
  - 增加打扰（悬浮 OSD、弹窗、通知）。
  - 引入需要用户持续管理的机制。

注意：判断「是否破坏」基于**默认路径**上的体验，而非高级用户可绕过的能力。

## Speeding vs Video Speed Controller 对照法

VSC（Video Speed Controller）是全功能派的代表：键盘快捷键矩阵、按钮式 OSD、
逐帧微调、自定义全局快捷键等。

- **凡 VSC 有而 Speeding 没有的功能**：默认先论证「是否有不可替代的存在理由」，
  不跟风补全。逐项对照：目标用户（学习者/追剧党）真的高频需要吗？不做会损失
  什么？加上是否破坏「set once and forget it」？
- **凡 Speeding 有而 VSC 没有的功能**（站点记忆、隐私零追踪、保持音调）：这是
  差异化资产，讨论时优先保护，任何新功能不得侵蚀它们的叙事。
- **结论形态**：每个功能给出「恰当 / 不恰当 / 可后置」+ 一句理由，供用户拍板。
